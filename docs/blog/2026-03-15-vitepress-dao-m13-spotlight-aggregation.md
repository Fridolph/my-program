# 2026-03-15 · 让场景入口开始长成更完整的问题路线

## 背景

M12 完成之后，站点已经拥有更清楚的视觉入口。

分类入口更像入口，scene 入口也更像入口，首页和 discover 的第一眼判断效率明显提升了。

但继续往下看时，新的问题也变得更清楚：

> 入口虽然变得更可视了，可是入口之间的上层关系还不够清楚。

尤其是一些长尾 scene，单独看并没有问题，但一旦用户面对的是一个更完整的页面问题，比如首屏、卡片展示、阅读反馈，就还是需要自己把几个 scene 拼起来。

这就是 M13 的起点。

## 这一轮怎么做

这一轮继续按同一条 Dao 节奏推进：

1. 先定义 M13 的目标、边界和业务流。
2. 把专题路线、scene 映射和路线页结构拆清楚。
3. 再把专题路线接入生成链路，稳定生成索引页与详情页。
4. 然后把首页和 discover 接成更高层的问题入口。
5. 开发完成后跑 `pnpm docs:check`，确认生成和构建都通过。
6. 自测通过后，再回写设计、任务、进度和开发笔记。

## 关键判断

### 1. 下一步不是继续加 scene，而是补 scene 之间的上层关系

当前站点已经有：

- 分类入口
- scene 入口
- tag 入口
- 难度入口

如果继续只往下加 scene，discover 会越来越像“入口清单”，而不是“问题路线”。

所以这一轮真正要补的，不是一个新字段，而是：

> 如何让多个 scene 形成一条更完整的进入路线。

### 2. 专题路线必须站在用户问题上，而不是站在数据字段上

这一轮我没有把专题路线做成“另一个分类页”。

路线页的核心不是告诉你“这里有哪些 scene”，而是告诉你：

- 你现在解决的是哪类问题
- 为什么适合从这里开始
- 先看哪些 scene
- 再看哪些 demo

这让路线页和普通索引页的角色完全不同。

### 3. 专题路线必须复用现有链路，而不是另起系统

这一轮没有新建一套独立内容系统。

路线页继续复用的仍然是：

- scene
- demo
- journal
- 页面级分享图
- sitemap

这样做的好处很直接：

路线页不会变成新的孤岛页面，而是自然长在现有发现链路上。

## 这轮代码上发生了什么

### 新增了专题路线元数据

这一轮为专题路线建立了独立元数据，包含：

- 路线标题
- 描述
- 为什么从这里开始
- 覆盖的 scene
- 推荐 demo
- 路线封面配置

这样路线不再是页面里手写的一组链接，而是变成站点内容结构的一部分。

### 生成链路开始产出专题路线页

这一轮生成了：

- `/discover/spotlights/`
- `/discover/spotlights/:slug`

这意味着专题路线已经进入主生成链路，而不是临时页面。

### 首页和 discover 开始承接更高层的问题入口

这一轮还把专题路线入口接入到了：

- 首页
- discover
- 侧边栏与导航

这样站点现在已经有两种进入方式：

1. 直接按单个 scene 进入。
2. 先按更完整的问题路线进入。

这对后续继续扩内容很重要，因为它让站点不再只是“入口更多”，而是“入口关系更清楚”。

## 自测

这一轮继续使用统一最小闭环：

```bash
pnpm docs:check
```

除此之外，我额外检查了四件事：

1. `/discover/spotlights/` 是否已经稳定生成。
2. 每条路线页是否都能回流到 scene 详情页和 demo 详情页。
3. 首页和 discover 是否已经出现专题路线入口。
4. 路线页是否已经进入 sitemap、release 快照和页面级分享图链路。

这轮自测通过，说明 M13 已经完成了从“scene 很多”到“问题路线更清楚”的闭环。

## 这一轮的结论

M13 最重要的变化，不是“又多了几页 discover 页面”，而是：

> 当前站点已经开始具备按完整问题路线进入的能力，而不只是按单个 scene 或分类进入。

这件事对内容站的长期维护很关键。

因为内容一旦继续增长，真正重要的不是再堆入口，而是让入口之间的关系越来越清楚。

## 后续方向

M13 到这里已经完成。后续自然还可以继续推进，例如：

1. 继续补更细的专题路线，让长尾 scene 进入更清楚的主题编排。
2. 继续扩展重点 demo 的深描范围，让路线页承接的案例质量更稳定。
3. 在路线与入口都稳定后，再评估是否需要补更强的检索和推荐能力。
