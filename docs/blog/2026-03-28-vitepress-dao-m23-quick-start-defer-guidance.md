# 2026-03-28 · 让 quick start 开始表达当前先不上什么

## 背景

M22 完成之后，quick start 已经开始告诉用户：

- 下一步该补哪一类
- 这一步对当前角色和当前阶段意味着什么

这让 quick start 的继续推进判断已经更完整了一层。

但新的缺口也很快变得很清楚：

> 当用户已经知道下一步可以补什么之后，他还是不容易判断当前先不上什么更稳，避免把节奏做重。

这就是 M23 要继续补上的语义。

## 这一轮怎么推进

这一轮继续按 Dao 节奏推进：

1. 先确认 M23 仍然沿着 quick start 主链路走，不另建新系统。
2. 梳理当前已经具备的字段和页面表达，确认“何时先不上”和“下一步建议”之间还缺一层反向推进判断。
3. 定义新的轻量字段：`deferTypes` 和 `deferReason`。
4. 让 quick start 详情页开始表达“当前先不急着补什么”。
5. 让角色页、阶段页与推进类型页开始聚合暂缓判断。
6. 把这层反向推进提示接回首页、discover 和 quick start 总览。
7. 开发完成后跑 `pnpm docs:generate`、`pnpm docs:build`、`pnpm docs:check`。

## 关键判断

### 1. 这一轮不做复杂取舍系统，只补最稳定的反向判断

M23 没有引入更复杂的推荐逻辑，也没有开始做“为什么补 A 而不是 B”的完整推理树。

因为当前最稳定的问题不是“判断不够复杂”，而是：

- 用户知道下一步该补什么
- 但还不知道当前先不上什么更稳

所以这一轮先补最稳定的一层反向推进语义。

### 2. 继续写回 quick start 主链路，不另开新模型

这一轮没有另外建“反向路线系统”。

而是继续把暂缓判断写回 `quickStartGuides`：

- `deferTypes`
- `deferReason`

然后由同一条生成链路统一产出 detail、segment、首页和 discover。

这样做的好处很直接：

- 内容判断仍然集中在 quick start
- 页面表达继续统一
- 维护成本不会突然变高

### 3. “先不上什么”比“再多给一个下一步”更能控制节奏

M20 解决的是下一步去哪。
M21 解决的是下一步属于哪一类。
M22 解决的是这一步对角色 / 阶段意味着什么。

M23 继续往前推进一层：

- 当前先不上什么更稳

这会让 quick start 不只是不断给更多入口，而开始帮助用户控制推进节奏。

## 这轮代码上发生了什么

### quick start 统一补了暂缓判断字段

这一轮为 quick start 统一补齐了：

- `deferTypes`
- `deferReason`

这样每条 quick start 不只会表达：

- 下一步更适合补什么

也开始表达：

- 当前先不急着补什么
- 为什么现在先不上更稳

### quick start 详情页开始表达“当前先不急着补什么”

这一轮最直观的变化，是 quick start detail 页在“下一步建议”之后，开始出现新的反向推进区块：

- 当前先不急着补什么

这个区块会继续回流到对应推进类型页，帮助用户理解：

- 不是当前所有好看的方向都要马上补
- 有些方向现在先不上，反而更稳

### 角色页、阶段页和推进类型页开始聚合暂缓判断

这一轮还把暂缓判断继续接回聚合页。

现在在：

- 角色页
- 阶段页
- 推进类型页

用户都能看到一层轻量的暂缓提示，而不只是正向推进建议。

这让这些页开始不只会回答“更适合往哪里走”，也开始回答“当前先别急着往哪里走”。

### 首页、discover 和 quick start 总览一起接入了反向推进提示

为了不把这层判断只放在 detail 页里，这一轮也把“先不上什么”的提示接回了入口层。

现在用户在：

- 首页
- discover
- quick start 总览

都能更早意识到：

> 当前继续推进时，不只是补什么更重要，不急着补什么同样重要。

## 自测

这一轮继续使用统一闭环：

```bash
pnpm docs:generate
pnpm docs:build
pnpm docs:check
```

除此之外，我额外重点核对了四件事：

1. quick start 详情页是否已经出现“当前先不急着补什么”区块。
2. 角色页、阶段页与推进类型页是否已经出现暂缓判断表达。
3. 首页、discover 与 quick start 总览是否已经出现反向推进提示。
4. 生成链路和 journal / og 资产是否仍保持稳定。

## 这一轮的结论

M23 最重要的变化，不是又多了一组字段，而是：

> 当前 quick start 已开始具备静态反向推进判断能力，能帮助用户避免在错误时机把节奏做重。

这会让 quick start 更像真正的节奏判断入口，而不只是不断给“下一步”。

## 后续方向

M23 到这里已经完成。后续自然还可以继续推进，例如：

1. 继续补“为什么先补 A 而不是 B”的更细取舍说明。
2. 继续把正向推进和反向推进串成更稳定的静态判断链。
3. 在静态取舍语义稳定之后，再评估是否值得做更细的路线编排。
