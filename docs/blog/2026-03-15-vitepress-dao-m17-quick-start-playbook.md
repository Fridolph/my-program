# 2026-03-15 · 让 quick start 不只告诉你去哪，也告诉你先怎么做

## 背景

M16 完成之后，站点已经有了 quick start。

用户可以按“我想先做首页首屏”或“我想先做阅读与加载反馈”这种问题直接进入内容，而不必先理解 scene、spotlight 和 demo 之间的关系。

但继续往下看时，新的问题也很明显：

> quick start 已经能把人送进去，可它还没有继续告诉用户第一步怎么做、怎么选、先避开什么。

这就是 M17 的起点。

## 这一轮怎么推进

这一轮继续按 Dao 节奏推进：

1. 先定义 M17 的目标、边界和新增字段。
2. 梳理 quick start 详情页还缺哪几层任务型建议。
3. 再补 `firstActions`、`chooseTips` 和 `avoidPitfalls`。
4. 接着让首页直接展示具体问题入口，而不只是总入口。
5. 开发完成后跑 `pnpm docs:check`，确认生成、构建和校验都通过。
6. 自测通过后，再回写设计、任务、进度和开发笔记。

## 关键判断

### 1. quick start 仍然要保持轻量

这一轮没有把 quick start 写成长教程。

它仍然是导览页，只是把最关键的三层建议补出来：

- 推荐步骤
- 怎么选
- 先避开什么

这样既能继续保持轻量，也能明显减少“我知道要看哪条线，但还是不知道第一步怎么做”的停顿。

### 2. 建议必须继续复用元数据主链路

这一轮没有手工改 quick start 单页 Markdown。

建议内容继续写回 `site-content`，再统一由生成模板输出。

这样后续如果继续补更多 quick start，只需要沿着同一条主链路补字段即可。

### 3. 首页要直接暴露具体问题入口

M16 的首页已经有 quick start 总入口。

但如果用户还要先点进总览页，仍然多了一次判断。

所以这一轮继续往前一步：

> 首页直接展示具体 quick start 条目。

这让“从问题直接开始”这件事真正进入首页第一层体验。

## 这轮代码上发生了什么

### quick start 详情页开始具备任务型建议结构

这一轮为现有四条 quick start 统一补齐了：

- `firstActions`
- `chooseTips`
- `avoidPitfalls`

生成后，quick start 详情页现在会明确告诉用户：

- 第一轮建议先做什么
- 面对不同情况该怎么选
- 有哪些常见误区应该先避开

这让 quick start 从“问题入口”开始更像“轻量任务导览”。

### 首页开始直接展示问题条目

这一轮首页新增了“按问题开始”区块。

和之前只给总入口相比，这一步让用户在首页就能直接选择：

- 先做首屏
- 先做卡片列表和预览
- 先做阅读与加载反馈
- 先找低成本练习案例

这让 quick start 的价值不再只停留在 discover 内部，而是真正进入首页的第一层判断。

## 自测

这一轮继续使用统一闭环：

```bash
pnpm docs:check
```

除此之外，我额外人工抽查了四件事：

1. quick start 详情页是否出现推荐步骤、选择建议和误区提醒。
2. 首页是否开始直接展示 quick start 条目。
3. quick start 与 spotlight、scene、demo、journal 的联动是否仍保持稳定。
4. release 快照、sitemap 和生成产物是否仍保持稳定。

这轮自测通过，说明 M17 已经完成了从“按问题开始”到“开始之后也知道怎么走第一步”的闭环。

## 这一轮的结论

M17 最重要的变化，不是“又多了几段文案”，而是：

> 当前 quick start 已经开始承担轻量任务型导览职责，而不再只是问题入口的跳转页。

这对内容站很重要。

因为真正有帮助的入口，不只是把用户送进去，更要在最开始那一步减轻判断负担。

M17 把这件事往前推了一步。

## 后续方向

M17 到这里已经完成。后续自然还可以继续推进，例如：

1. 继续补更多 quick start 条目，覆盖不同项目阶段和不同人群。
2. 继续把团队协作、内容运营和页面改造类任务也做成起步线。
3. 在 quick start 足够稳定之后，再评估是否需要更强的推荐或更细的任务编排层。
