# 2026-03-15 · 让用户按当前问题直接开始

## 背景

M15 完成之后，站点已经有：

- 更密的专题路线
- 更完整的长尾 scene narrative
- 更稳定的详情页解释层

这时新的问题也自然冒出来了：

> 如果第一次进入站点的用户并不想先理解这些结构，他能不能直接按“我现在想做什么”开始？

这就是 M16 要解决的问题。

## 这一轮怎么推进

这一轮继续按 Dao 节奏推进：

1. 先定义 M16 的目标、边界和问题集合。
2. 梳理 quick start 如何映射到 spotlight、scene 和 demo。
3. 再生成快速开始总览页与详情页。
4. 接着把首页、discover 和导航入口同步接上。
5. 开发完成后跑 `pnpm docs:check`，确认生成、构建和校验都通过。
6. 自测通过后，再回写设计、任务、进度和开发笔记。

## 关键判断

### 1. 不把重搜索拉回来

这一轮没有重新启用本地搜索。

不是因为搜索不重要，而是因为当前站点规模更适合先补一层更轻的导览：

> 用户不一定需要搜关键词，他很多时候只是想知道“我现在该先看哪里”。

所以 M16 先补的是 quick start，而不是搜索框。

### 2. quick start 不是新分类，而是问题入口

这一轮新增的并不是第四套分类系统。

quick start 回答的是更贴近任务的话：

- 我想先做首页首屏
- 我想先做卡片列表与内容预览
- 我想先做阅读与加载反馈
- 我想先找低成本练习案例

它的角色不是替代 spotlight 或 scene，而是作为更轻的起点，把用户送进现有主链路。

### 3. quick start 必须继续复用现有内容结构

这一轮没有新建独立内容系统。

quick start 详情页继续回流到：

- spotlight
- scene
- demo
- journal

这让它不是一次性页面，而是继续长在站点现有内容结构上的导览层。

## 这轮代码上发生了什么

### 生成链路开始产出 quick start 页面

这一轮新增了：

- `/discover/quick-start/`
- `/discover/quick-start/:slug`

这意味着 quick start 已经进入生成主链路，也进入了 sitemap、release 快照和页面级分享图映射。

### quick start 开始承担“第一次选择”的职责

以前用户第一次进入时，更容易碰到的问题是：

- 先看 scene？
- 先看 spotlight？
- 先看 demo？

这一轮之后，用户可以先从一个更贴近当前问题的入口开始。

它不要求用户先理解站点结构，而是先给出更直白的起步线。

### 首页与 discover 一起承接 quick start

如果 quick start 只生成页面而不接入口，用户还是感受不到这层变化。

所以这一轮同步把 quick start 接入了：

- 首页内容入口
- discover
- 顶部导航
- discover 侧边栏

这让 quick start 不只是“站内有这页”，而是“用户真的能走进去”。

## 自测

这一轮继续使用统一闭环：

```bash
pnpm docs:check
```

除此之外，我额外人工抽查了四件事：

1. `/discover/quick-start/` 是否稳定生成。
2. quick start 详情页是否能回流到路线、场景和案例。
3. 首页与 discover 是否已出现 quick start 入口。
4. sitemap、release 快照与页面级分享图是否仍保持稳定。

这轮自测通过，说明 M16 已经完成了从“入口已经很多”到“可以按当前问题直接开始”的闭环。

## 这一轮的结论

M16 最重要的变化，不是“又多了几页 discover 页面”，而是：

> 当前站点已经开始提供一层轻量检索替代入口，让用户不用先理解结构，也能直接开始。

这对内容站很重要。

因为当内容继续增长时，真正决定体验的，不只是内容有没有被组织好，而是：

- 新用户能不能很快找到起点
- 起点能不能把他自然送进现有结构

M16 把这件事往前推了一步。

## 后续方向

M16 到这里已经完成。后续自然还可以继续推进，例如：

1. 继续补更细的 quick start 问题类型，覆盖更多任务场景。
2. 继续把团队协作、内容运营或页面改造类问题也做成起步线。
3. 在 quick start 与路线都稳定之后，再评估是否需要补更强的检索或推荐机制。
