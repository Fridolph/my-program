# 2026-03-15 · 让站点回到“内容入口优先”的轻量构建状态

## 背景

M10 完成之后，站点已经具备：

- 更完整的 demo 内容页
- 更稳定的场景入口
- 更清楚的 discover / explore 流转

但在最近几轮验证里，有一个问题开始越来越明显：

> 站点的内容入口已经足够丰富了，但构建仍然在为本地搜索索引付出一笔越来越重的客户端成本。

这件事带来的影响并不只是一个 build warning。

它同时会表现成：

- header 被搜索框挤压
- 客户端产物变重
- 内容发现方式变得模糊：到底是靠搜索，还是靠已经建立起来的内容入口？

所以 M11 这一轮，我继续按 Dao 的节奏往前推：

> 让站点回到“内容入口优先”的轻量构建状态。

## 这一轮怎么做

这一轮继续按统一节奏推进：

1. 先定义 M11 的目标、边界和业务流。
2. 明确构建热点、可移除负担与发现 fallback 三类对象。
3. 再把本地搜索入口收掉，并补清楚预览与构建说明。
4. 开发完成后跑 `pnpm docs:check`，确认 build 不再出现本地搜索超大 chunk 告警。
5. 自测通过后，再回写设计、任务、进度和开发笔记。

## 关键判断

### 1. 先移除高成本低收益能力，而不是急着替换成另一套搜索方案

这一轮没有引入新的搜索服务，也没有继续在本地搜索上做更复杂的拆分实验。

原因很简单：

- 当前站点的主要入口已经有首页
- 有 discover
- 有 explore
- 有分类页
- 还有 demo 页内部回流

也就是说，搜索不再是唯一入口。

在这种前提下，先收掉高成本的本地搜索，是一个比“继续维护一个越来越重的搜索框”更合理的选择。

### 2. header 的空间问题，本质上也是信息优先级问题

从界面上看，它像是“header 放不下了”。

但从结构上看，它其实是在问：

> 当前站点最优先暴露给用户的，到底是什么？

这轮的答案是：

- 项目指南
- 内容入口
- Demo 分类

而不是继续把一个高成本搜索框放在最前面。

### 3. 轻量化不能让预览链路变模糊

如果只是把搜索收掉，但不把预览方式说清楚，开发体验会退步。

所以这轮我同时把这件事写回了文档：

- `docs:dev` 负责开发态快速回看
- `docs:preview` 负责最终产物验证

这样轻量化之后，验证链路反而更清晰。

## 这轮代码上发生了什么

### 本地搜索入口被移除了

这一轮直接收掉了 `themeConfig.search`。

结果很直接：

- header 不再显示搜索框
- build 不再继续生成本地搜索索引 chunk
- 内容发现重新回到当前已经建好的入口结构

### 构建告警收敛了

这一轮最明显的结果之一，就是 build 时不再出现本地搜索索引超大 chunk 告警。

这不是一个“看起来更干净”的小优化，而是一次很明确的维护性改善：

它意味着站点的长期增长，不再继续被一个高成本搜索索引放大。

### 预览说明被写回文档了

这一轮还把 `docs:dev` 和 `docs:preview` 的用途写回到了发布说明里。

这样之后无论是谁接手这个仓库，都不用再猜：

- 我要改内容时该怎么预览
- 我要验最终产物时该怎么预览

## 自测

这一轮继续用统一最小闭环做自测：

```bash
pnpm docs:check
```

除此之外，我还额外做了三类检查：

1. 检查 build 是否不再出现本地搜索索引超大 chunk 告警。
2. 检查 header 是否已经不再显示搜索框。
3. 检查发布说明中是否已经明确写回 `docs:dev` 和 `docs:preview` 的分工。

这轮自测通过，说明构建性能和预览说明都已经完成闭环。

## 这一轮的结论

M11 最重要的变化，不是“少了一个搜索框”，而是站点对外和对内的主逻辑都更清楚了：

> 当前站点的内容发现方式，已经不再依赖高成本搜索，而是正式转向清晰的内容入口结构。

这意味着它在长期维护上会更轻，也更稳定。

## 后续方向

M11 到这里已经完成。后续自然还可以继续推进，例如：

1. 如果未来内容规模进一步扩大，再重新评估更适合当前站点的搜索方案。
2. 继续把长尾 demo 的深描和长尾场景的 narrative 补起来。
3. 在入口和性能都稳定后，再看是否需要做更细的产物分包或性能画像。
