# 2026-03-14 · 让 metadata 真正长成站点导航

## 背景

M4 完成之后，站点已经不只是 demo 列表，也不只是内容入口集合了。

它已经具备：

- 分类浏览
- 专题发现
- 开发笔记
- 内容与案例双向连接

但继续往前看，还有一个很明显的问题没有解决：

> 用户仍然主要依赖分类目录找内容。

这意味着，只要用户不知道 demo 属于哪一类，就会在入口处卡一下。

而仓库里其实已经有不少更有价值的 metadata：

- `tags`
- `scenes`
- `difficulty`

这些字段过去主要用于生成说明和相关推荐，但还没有真正成为“导航结构”。

所以 M5 这一轮，我做的核心动作不是再加一种内容，而是：

> 让 metadata 从内容补充字段，变成站点可以直接走进去的路径。

## 这一轮怎么做

这一轮仍然严格按 Dao 节奏推进：

1. 先定义 M5 的目标、边界和业务流。
2. 再明确哪些 metadata 要升级为导航维度。
3. 然后实现多维导航页和 demo 页回流入口。
4. 开发完成后跑 `pnpm docs:generate` 和 `pnpm docs:build`。
5. 自测通过后，再回写设计、任务、进度和开发笔记。

## 关键判断

### 1. 先把已有 metadata 变成导航，不先上复杂筛选器

这轮我没有先做客户端筛选、外部搜索或更重的检索系统。

原因很简单：当前站点已经有足够多的结构化字段，真正缺的是“把这些字段变成入口”，而不是再引入一套更复杂的系统。

所以 M5 先做静态可生成的多维导航闭环：

- 标签导航
- 场景导航
- 难度导航

### 2. 多维导航必须回到 demo 主链路

我没有把 `/explore/` 做成一个只看不走的索引页。

这一轮的判断很明确：所有维度页都必须回到 demo 详情页，否则它就只是另一个列表。

所以每个维度页都统一承接三层内容：

- 推荐先看
- 全部案例
- 相关开发笔记

这样多维导航页不是终点，而是一个中转站。

### 3. demo 页也要能回到维度导航

如果只有 `/explore/ -> demo` 单向链路，那用户还是很难在浏览过程中切换到别的发现方式。

所以这轮我也给 demo 页补了“多维入口”：

- 按标签继续找
- 按场景继续找
- 按难度继续找

这一步很关键，因为它让 demo 页第一次具备“切换导航维度”的能力。

## 这轮代码上发生了什么

### 新增了多维导航主入口

站内新增了 `/explore/`，把标签、场景、难度三类入口统一收口。

这让站点开始有一个明确的“不是按目录找”的入口。

### 三类维度都变成了可访问页面

这一轮继续复用生成脚本，把三类维度全部产生成独立页面：

- `/explore/tags/`
- `/explore/scenes/`
- `/explore/difficulty/`

并且每个条目都有自己的详情页。

### demo 页开始具备维度回流

这轮之后，demo 详情页里原本的标签、场景、难度不再只是说明文字，而是可以直接跳转的导航入口。

这让用户在看具体案例时，不需要退回首页或分类页，也能切换浏览方式。

## 自测

这一轮继续使用统一的最小闭环自测：

```bash
pnpm docs:generate
pnpm docs:build
```

这轮除了命令通过，我还重点检查了这些点：

- `/explore/` 是否正常生成。
- 标签、场景、难度索引页和详情页是否都可访问。
- demo 页是否出现新的多维入口。
- 顶部导航、侧边栏、首页和专题发现页是否都接上了多维导航入口。
- 原有分类页、详情页、相关阅读和开发笔记链路是否没有被破坏。

这轮自测通过，新增的多维导航没有破坏已有主链路。

## 这一轮的结论

M5 最重要的变化，不是“又多了一组页面”，而是站点里一类很关键的结构发生了变化：

> metadata 开始从内容字段，变成导航骨架。

这意味着站点不再只能按目录组织内容，而开始能按问题、场景和复杂度组织内容。

## 后续方向

M5 到这里已经完成。下一步自然可以继续往更深的发现能力推进，例如：

1. 继续补足更多高质量场景 metadata，减少单条场景过散的问题。
2. 把多维导航继续扩展到专题页、精选页和内容页之间。
3. 在静态导航稳定之后，再评估是否需要更重的筛选或搜索增强。
