# 2026-03-14 · 让展示站开始承载内容，而不只是承载 demo

## 背景

前面的几轮重构已经把站点的基础能力立住了：

- M1 收口了内容治理。
- M2 补通了浏览链路。
- M3 收口了发布与运维入口。

走到这里，站点已经不再只是“能访问的 demo 集合”。但它还不算一个真正的内容站，因为很多关键经验仍然停留在仓库文档里，而不是站点本身的一部分。

所以 M4 这一轮，我没有先做更重的专题系统，也没有先做新的视觉包装，而是先完成一个更基础的动作：

> 让开发笔记、阶段经验和专题发现，开始成为站点入口的一部分。

## 这一轮怎么做

这一轮还是严格按 Dao 的节奏推进：

1. 先定义 M4 的内容模型和业务流。
2. 再明确新增内容页应该落在哪一层。
3. 然后做页面生成与入口接入。
4. 开发后继续跑 `pnpm docs:generate` 和 `pnpm docs:build`。
5. 自测通过后，再回写文档和里程碑记录。

## 关键判断

### 1. 先定义内容类型，而不是先铺页面

M4 先定义了两类内容入口：

- `journal`：承载阶段开发笔记和过程记录。
- `discover`：承载专题发现、场景入口和精选线索。

这样做的好处是，后续继续扩展时，我们不会重新回到“每篇内容单独找地方挂”的状态。

### 2. 继续复用已有内容资产

这轮没有引入新的 CMS，也没有重做文档系统，而是优先复用已经存在的资产：

- `docs/blog/` 里的阶段笔记
- 现有的 `featured`、`scenes` 和分类数据
- 已经存在的生成脚本主链路

这让 M4 能在低风险下先跑出一个闭环。

### 3. 内容入口和 demo 入口必须互通

我没有把内容页做成和 demo 完全分离的区域，而是让它们继续挂在同一个文档站里。

这样用户可以：

- 从首页进入开发笔记，再回到项目进度和 demo 入口。
- 从专题发现页按场景进入 demo。
- 从首页同时看到“看案例”和“读过程”两种入口。

## 这轮代码上发生了什么

### 开发笔记开始进入站点主入口

这一轮新增了站内开发笔记索引页和内容页，让已有阶段记录开始变成站内可读内容，而不是只留在仓库源文档中。

### 专题发现页开始承接多维浏览线索

这一轮新增了 `/discover/`，把场景、精选和分类导览收口到一个更适合作为内容入口的页面上。

### 首页开始具备“内容产品入口”

首页除了分类浏览、精选 demo 和按场景开始之外，又多了一层内容入口：

- 开发笔记
- 专题发现

这一步非常关键，因为它让站点正式具备“内容入口页”的角色，而不再只是 demo 导航页。

## 自测

这轮继续使用统一的最小闭环自测：

```bash
pnpm docs:generate
pnpm docs:build
```

自测通过后，我又额外检查了下面这些点：

- `/journal/` 是否能进入笔记列表和详情页。
- `/discover/` 是否能正常显示场景、精选和分类导览。
- 首页是否已经出现新的内容入口模块。
- 导航与侧边栏是否已经接入“开发笔记”和“专题发现”。

这一轮没有出现阻塞当前主链路的问题，新增内容页与 demo 链路可以并行工作。

## 这一轮的结论

M4 这一轮最重要的变化，不是“页面又多了两个”，而是站点开始出现新的产品事实：

> 项目的经验、设计和阶段判断，开始变成站点可以直接阅读和浏览的内容。

这意味着站点已经不只是案例库，也开始变成知识入口。

## 下一步

M4 第一轮先完成的是内容模型和入口闭环。接着在第二轮里，我继续把重点放在“内容关系”上，而不是再去扩新的页面类型。

## 第二轮继续做了什么

第二轮主要解决一个很具体的问题：

> 内容页和 demo 页虽然已经都在站内了，但它们还没有真正互相解释。

如果只停留在第一轮，用户会遇到两个断点：

- 读完开发笔记，不知道接下来该看哪几个 demo。
- 看完 demo，也不知道哪些阶段笔记解释了背后的判断和取舍。

所以第二轮没有再扩新页面，而是先把这条关系链补上。

### 1. 用一份关系数据统一承接双向链路

我没有分别给 `journal` 页和 `demo` 页各做一套配置，而是把关联真值统一放回 `journalEntries`：

- 每篇笔记显式声明 `relatedDemoIds`
- 内容页直接读取这组 demo
- demo 页反向读取哪些笔记关联了自己

这样做的好处是很直接的：双向入口只维护一份关系，不会越改越散。

### 2. 开发笔记页开始变成“可继续浏览”的页面

第二轮之后，开发笔记页不再只是一个说明页，而是多了三层继续浏览入口：

- 相关 Demo
- 继续阅读
- 邻接笔记

这让内容页开始真正承担“带用户继续往下走”的角色，而不是读完就结束。

### 3. demo 详情页开始能回到“为什么这样做”

第二轮也给 demo 详情页补了“相关阅读”。

这一步对站点很重要，因为 demo 页原本只回答“这是什么、怎么预览、还能看什么案例”，现在开始能进一步回答：

> 这条案例在哪个阶段判断里被讨论过。

这让案例页不再只是结果页，也开始连回过程页。

## 第二轮自测

第二轮仍然沿用同一套最小闭环自测：

```bash
pnpm docs:generate
pnpm docs:build
```

这次除了命令通过，我还重点检查了这些点：

- 开发笔记页是否出现“相关 Demo”。
- 开发笔记页是否出现“继续阅读 / 邻接笔记”。
- 被引用的 demo 页是否出现“相关阅读”。
- 原有 demo 详情页的“邻接导航 / 相关推荐”是否仍然正常。

第二轮自测通过，新增关系入口没有破坏原有主链路。

## 这一轮 M4 的最终结论

M4 到这里，已经不只是“站里有内容页”了，而是进一步形成了一个更完整的事实：

> 内容页可以带人去看案例，案例页也可以把人带回到过程和判断。

这意味着站点从“内容入口”继续推进到了“内容关系”。

## 后续方向

M4 当前已经完成。后续自然可以继续往更深的内容产品化方向推进，例如：

1. 扩展更多开发笔记和专题页。
2. 把关联模型继续扩展到专题页、场景页和精选策展页。
3. 继续推进分享图、专题包装和更完整的内容导航体系。
