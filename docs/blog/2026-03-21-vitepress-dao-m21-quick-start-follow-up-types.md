# 2026-03-21 · 让 quick start 的下一步开始区分推进类型

## 背景

M20 完成之后，quick start 已经开始告诉用户：

- 第一版做完之后，下一步可以接哪条 quick start
- 为什么这一步值得继续接

这让 quick start 不再只停在“起步线入口”。

但新的缺口也马上变得很清楚：

> 当用户已经知道下一步去哪之后，他还是不容易判断当前到底该先补结构、补反馈、补首屏氛围，还是补一点局部动效。

这就是 M21 要解决的问题。

## 这一轮怎么推进

这一轮继续按 Dao 节奏推进：

1. 先定义 M21 的目标、边界和推进类型模型。
2. 梳理 M20 的 follow-up 字段还缺什么语义。
3. 为 quick start 补 `followUpTypes`。
4. 让 quick start 详情页的下一步建议开始显示推进类型。
5. 生成按推进类型聚合的索引页和详情页。
6. 把推进类型入口接回 quick start 总览、首页和 discover。
7. 开发完成后跑 `pnpm docs:generate`、`pnpm docs:build`、`pnpm docs:check`。
8. 自测通过后，再回写设计、任务、进度、路线图、开发笔记和交接说明。

## 关键判断

### 1. 这一轮不做新的推荐系统，只补静态推进语义

M21 没有引入用户状态，也没有引入动态推荐逻辑。

因为当前最稳定的需求不是“更复杂的推荐”，而是把已经存在的下一步建议说得更清楚：

- 这一步是在补内容入口
- 还是在补反馈节奏
- 还是在补首屏氛围
- 还是在补局部动效

这层语义已经足够帮助用户判断当前推进重点。

### 2. 推进类型要继续留在 quick start 主链路里

这一轮没有另外建一套“推进系统”。

而是继续把推进类型写回 `quickStartGuides`，然后让生成链路统一产出：

- quick start 详情页
- quick start 总览页
- 首页
- discover
- 推进类型索引页
- 推进类型详情页

这样后续继续扩展时，仍然只需要沿着 quick start 主链路往前推。

### 3. “知道下一步去哪”要进一步长成“知道下一步为什么先补这一类”

M16 解决的是“从哪里开始”。
M17 解决的是“开始之后先做什么”。
M18 解决的是“值不值得现在做”。
M19 解决的是“谁来做、在哪个阶段做”。
M20 解决的是“第一版之后下一步去哪”。

M21 继续往前推进一层：

- 下一步为什么先补这一类

这样 quick start 的继续推进能力就更像一条静态的判断链，而不只是链接推荐。

## 这轮代码上发生了什么

### quick start 统一补了推进类型字段

这一轮为现有 quick start 统一补齐了：

- `followUpTypes`

这样每条 quick start 的下一步不再只是目标链接，也开始具备明确语义。

例如，用户现在不只会看到“下一步去卡片列表”，还会看到：

- 这一步是在补内容入口

这比单纯跳链接更容易帮助用户理解推进顺序。

### quick start 详情页的下一步建议开始显示推进类型

这一轮最直观的变化，是 quick start 详情页的“下一步建议”区块已经不只显示目标条目。

它现在同时会表达：

- 下一步属于哪一种推进类型
- 为什么现在先补这一类
- 如何回看到这一类推进类型的聚合页

这样用户在 detail 页里就能完成“下一步去哪”和“下一步为什么这样接”的双重判断。

### 站内新增了按推进类型回看的入口

这一轮还新增长出了一组新的 quick start 入口：

- `/discover/quick-start/follow-up/`
- `/discover/quick-start/follow-up/[slug]`

这组页面不再按角色、阶段或问题开始，而是按：

- 补内容入口
- 补反馈节奏
- 补首屏氛围
- 补局部动效

把常见推进顺序重新聚合起来。

### 首页、quick start 总览和 discover 一起接入了推进类型入口

M21 还把推进类型入口同步接回到了入口层。

现在用户在：

- 首页
- quick start 总览页
- discover

都能直接看到推进类型入口。

这让用户不一定要先点进某条 quick start 详情页，才意识到下一步的推进差异。

## 自测

这一轮继续使用统一闭环：

```bash
pnpm docs:generate
pnpm docs:build
pnpm docs:check
```

除此之外，我额外人工抽查了四件事：

1. quick start 详情页的下一步卡片是否已经显示推进类型。
2. `/discover/quick-start/follow-up/` 和对应详情页是否已经生成。
3. 首页、quick start 总览和 discover 是否已经出现推进类型入口。
4. sitemap、release snapshot 和页面级分享图链路是否仍保持稳定。

如果这些都通过，就说明 M21 已经完成了“下一步去哪”到“下一步为什么先补这一类”的闭环。

## 这一轮的结论

M21 最重要的变化，不是多了一个 follow-up 目录，而是：

> 当前 quick start 已开始具备静态推进类型语义，能把继续推进解释成更容易判断的结构、反馈、氛围和局部动效四类方向。

这会让 quick start 更像一个真正能陪用户往前走的入口，而不是只负责把用户送到第一步。

## 后续方向

M21 到这里已经完成。后续自然还可以继续推进，例如：

1. 继续把推进类型和角色 / 阶段交叉起来。
2. 继续补“现在先不上什么”的反向推进语义。
3. 在静态推进类型稳定之后，再评估是否值得继续细化更多推进层。
