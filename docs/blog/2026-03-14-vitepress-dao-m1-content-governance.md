# 2026-03-14 · 用 Dao 流程完成 VitePress 内容治理收口的第一轮里程碑

## 背景

前面的重构已经把仓库从静态 demo 集合推进成了 VitePress 展示站，也已经有了 metadata override、目录级 preset、首页精选和封面资源。

但继续往下做时，问题也很明显：

- 站点已经能生成，但内容质量还不够稳定。
- 标题、描述、slug、tags 和推荐理由虽然都在 metadata 里，却还没有形成一套统一判断。
- 如果直接继续加页面或加视觉，很容易把“能展示”和“可维护”重新混在一起。

所以这一轮我没有先做样式，也没有先加新功能，而是先按 Dao 的方式，把“内容治理如何运转”这件事收口清楚。

## 这轮怎么做

这一轮我先把开发流程固定下来，再按子任务推进：

1. 先做里程碑规划和业务流程梳理。
2. 再给每个子任务写详细设计。
3. 开发后必须跑 `pnpm docs:generate` 和 `pnpm docs:build`。
4. 自测通过后，把进度、过程、设计和解决方案回写到里程碑文档。
5. 每个子任务单独做一次 Dao Commit。

这样做的好处很直接：

> 每一步都不只是“改了代码”，而是在留下系统为什么这样变化的记录。

## M1 实际拆分

这轮 M1 最终拆成了 6 个子任务。

### T1：建立内容质量基线

这一轮没有马上改 demo，而是先回答：

- 什么样的 metadata 才算达标
- 哪些问题属于人工判断
- 哪些问题适合后面回到脚本里兜住

这一步把后面所有子任务的判断语言先统一了。

### T2：收口 slug、标题和描述语义

我先挑了一批最典型的条目做首轮语义收口：

- 系列目录里仍然保留编号式标题的条目
- 描述被页面碎片文本误命中的条目
- slug 仍然偏路径化的条目

这一步最重要的结论是：

- 系列目录问题优先回到 preset
- 单条精修问题继续留在 override

### T3：整理 tags、difficulty 和 scenes

标题和描述更像内容之后，站点还需要更像“可发现的资料库”。

所以这一轮我做了两件事：

- 重新整理一批重点 demo 的 tags 和 difficulty
- 新增轻量 `scenes` 字段，并把它接进详情页

我没有把 `scenes` 立刻扩到首页和分类页，因为当前阶段先验证 metadata 和详情页闭环更稳。

### T4：收口首页精选标准

首页精选已经能跑，但之前更像“已经挑好的条目”。

这一轮我把它进一步收口成三类角色：

- 视觉入口型
- 能力展示型
- 内容导航型

然后再精修少数精选条目的标题、推荐理由和 cover 语义，让策展层和基础内容层对齐。

### T5：把规则回写到生成链路

前面几轮证明稳定的结构规则，最终都回到了 `scanDemos()` 的统一校验里。

现在生成链路已经能兜住这些问题：

- 缺失 `title` / `description` / `id`
- 空 `tags`
- 非法 `difficulty`
- featured 缺少 `reason`
- 非法 `scenes`

这一步让我更确定一件事：

> 内容治理要想长期成立，必须有一层系统兜底，而不是只靠人工记忆。

### T6：收口里程碑文档

最后这一轮不是再补功能，而是把这次里程碑收束成完整记录。

包括：

- 设计文档
- 任务文档
- 子任务过程记录
- 这篇开发笔记

## 这轮代码上真正发生了什么

如果只看代码，这轮最核心的变化其实就三类。

### 1. metadata 变得更像内容系统

这轮继续强化了两层分工：

- preset 负责系列目录和共享语义
- override 负责单条精修和策展补充

这样一来，历史 demo 不再只是从 `public/` 扫出来的文件，而是逐步进入结构化治理状态。

### 2. demo registry 变成内容治理汇合点

这轮把 `scenes` 支持和结构校验都放回了 `docs-site/scripts/demo-registry.mjs`。

这样 `docs:generate` 和 `docs:build` 共用一套内容约束，不会出现本地生成一套、构建又一套的问题。

### 3. 详情页开始承载场景表达

在不做大改版的前提下，这轮让详情页多承担了一层工作：

- 不只告诉你“是什么”
- 也告诉你“适合用在哪”

这是一个很小的改动，但它会直接影响后面 M2 的浏览体验升级。

## 自测

这轮每个子任务完成后，我都重复做同一套最小闭环自测：

```bash
pnpm docs:generate
pnpm docs:build
```

在涉及 metadata 和详情页变化时，我还额外抽查了生成结果，确认：

- slug 没有冲突
- 目标 demo 的标题、描述和 tags 已按预期更新
- `scenes` 正常进入详情页
- 首页精选没有因为 metadata 收口而失效

这一轮没有出现需要回滚的情况，所有子任务都在自测通过后才进入下一个步骤。

## 这轮最重要的结论

这轮让我更确定一件事：

> VitePress 重构真正难的，不是把页面生成出来，而是把“内容如何被命名、被解释、被推荐、被校验”整理成一套稳定机制。

当这层机制成立之后：

- metadata 不再只是配置表
- 首页精选不再只是挑选结果
- 生成链路不再只是 Markdown 工厂

它们开始一起构成一个能持续迭代的内容系统。

## 下一步

M1 收口之后，下一步自然进入 M2 浏览体验升级。

优先方向会更聚焦在：

1. 首页、分类页和详情页之间的内容流转。
2. `scenes`、tags 和精选信息在浏览路径上的进一步消费。
3. 让站点更像“文档/博客式内容入口”，而不只是分类目录。
