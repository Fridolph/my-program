# 2026-03-15 · 让发布链路可回看，让旧入口真正完成收敛

## 背景

M6 完成之后，站点已经具备：

- 内容结构
- 多维导航
- 基础 SEO 与分享能力

从“站点内容”这件事看，已经比较完整了。

但再往后走，我发现还有一层很容易被忽略、但其实非常关键的事情没有完全收口：

> 发布链路虽然能跑，旧入口虽然已经不是默认入口，但这两件事还没有真正进入统一的工程语义。

也就是说：

- 维护者知道命令怎么跑，但不一定能在站内回看完整发布方式。
- workflow 能部署，但缺少对关键产物的明确校验。
- `views/index.html` 已经退位，但还没有完全纳入“新主站默认入口”的说明体系。

所以 M7 这一轮，我没有继续加新页面，也没有继续扩内容能力，而是做了一件更基础的事：

> 让发布链路可回看、可校验，也让旧入口真正完成语义收敛。

## 这一轮怎么做

这一轮继续严格按 Dao 节奏推进：

1. 先定义 M7 的目标、边界和业务流。
2. 再明确发布说明、CI 校验和旧入口收敛三类对象。
3. 然后把发布说明页、workflow 校验和旧入口改造一起落下去。
4. 开发完成后跑 `pnpm docs:check`，并模拟 workflow 的关键文件校验。
5. 自测通过后，再回写设计、任务、进度和开发笔记。

## 关键判断

### 1. 先把发布事实写进站内，而不是只留在 workflow 里

如果发布事实只存在于 `.github/workflows/static.yml`，它对维护者来说还是太隐蔽了。

所以这一轮我先新增了 `/guide/deployment`。

这样做的意义很直接：

- 发布方式不再只是“看 CI 配置的人才知道”
- 仓库内和站点内都有稳定的回看入口
- 以后继续演进发布链路时，也有明确文档挂点

### 2. workflow 要校验关键结果，而不是只负责“尽量构建完”

发布自动化最怕的不是构建失败，而是“构建通过了，但关键文件没进产物”。

所以这轮在 workflow 里我加的不是花哨步骤，而是最朴素的关键文件校验：

- `index.html`
- `sitemap.xml`
- `robots.txt`
- `manifest.webmanifest`
- `views/index.html`

这让发布从“能跑”变成“结果可验证”。

### 3. 旧入口不删，但必须完成收敛

这轮没有删除 `views/index.html`。

原因很明确：它还承担历史链接兜底作用。

但它也不能继续像一个平行入口那样存在。

所以我做了三件事：

- 补 `noindex,follow`
- 补 canonical 到主站
- 补到“发布说明”的明确跳转

这样旧入口保留了，但它的角色已经被收紧成“迁移说明页”。

## 这轮代码上发生了什么

### 站内新增了发布说明页

这一轮新增了 `/guide/deployment`，把本地命令、workflow 步骤、关键校验项和旧入口说明统一收口。

这样维护者不用再在 README、workflow 和历史记忆之间来回切。

### GitHub Pages workflow 开始做关键产物校验

这一轮 workflow 除了部署，还会显式检查关键产物。

这一步非常重要，因为它把“产物里应该有什么”从隐性常识变成了显性规则。

### 旧入口正式纳入迁移说明体系

`views/index.html` 现在不只是跳转页了，而是：

- 明确声明它不是默认入口
- 明确指向新主站
- 明确指向发布说明
- 通过 noindex 避免继续抢主站入口语义

## 自测

这一轮继续按统一的最小闭环做自测：

```bash
pnpm docs:check
```

除此之外，我还额外做了两类检查：

1. 模拟 workflow 中的关键产物校验。
2. 检查发布说明页和旧入口中的 canonical / noindex 是否存在。

这轮自测通过，发布说明、workflow 校验和旧入口收敛三条链路是连起来的。

## 这一轮的结论

M7 最重要的变化，不是“多了一页发布说明”，而是站点工程语义里有一层很关键的东西被补齐了：

> 发布开始从一个隐性动作，变成一个可以回看、可以验证、可以解释的工程环节。

同时，旧入口也终于不再是一个游离状态的历史遗留，而是被明确收敛进了新主站体系。

## 后续方向

M7 到这里已经完成。后续自然可以继续往更完整的工程化方向推进，例如：

1. 继续补页面级专属分享图与更细的对外呈现。
2. 在发布链路稳定后，再考虑更进一步的自动化回滚或发布监控。
3. 逐步继续削弱历史入口和旧目录的认知权重，让主站语义更统一。
