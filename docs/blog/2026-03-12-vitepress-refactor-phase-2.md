# 2026-03-12 · VitePress 重构第二阶段记录

## 背景

第一轮重构已经把 demo 仓库搬进了 VitePress，但我很快发现一个问题：站点虽然已经“像个站”，却还没有变成一条稳定的内容生产链路。

最明显的症状有三个：

- `public/` 里有大量 demo 没有进入站点。
- 侧边栏没有和真实页面同步。
- 预览组件在刷新和脚本型 demo 上不够稳。

所以这次没有继续做表层美化，而是回到主链路，先补内容发现、页面生成、导航同步和预览稳定性。

## 这次做了什么

### 1. 把 demo 扫描逻辑单独收敛成 registry

我新增了 `docs-site/scripts/demo-registry.mjs`，让它负责统一扫描 `public/`、识别分类、生成元数据。

这样后面不管是首页、分类页、详情页，还是 sidebar，都从同一份数据出发，不再各自写一套扫描逻辑。

### 2. 重写页面生成脚本

原来的生成逻辑只能覆盖部分 HTML 文件，而且更像一次性脚本。

这次我把它改成：

- 先清理旧的生成结果。
- 再按 registry 结果生成首页、分类页、详情页。
- 最后把 sidebar 输出成 `.vitepress/generated/demo-sidebar.mjs`。

这样站点结构就可以跟着 `public/` 的真实内容一起生长。

### 3. 把生成接入开发和构建入口

我在 `docs-site/package.json` 里增加了 `predev` 和 `prebuild`。

这样无论是本地跑开发环境，还是 CI 构建发布，都会先做一次生成，避免“源码变了，站点没跟上”的漂移。

### 4. 修正 Shadow DOM 预览的两个关键问题

我顺手补了 `DemoPreview.vue` 的几个硬伤：

- 避免重复 `attachShadow` 导致刷新时报错。
- 用 `demoUrl` 重新计算相对资源路径。
- 对脚本节点做重放，让依赖 JS 的 demo 有机会在预览容器里跑起来。

这一步不保证所有老 demo 都 100% 还原，但至少把预览体验从“经常坏”提升到了“多数可用，并且有原始页面兜底”。

## 这次最大的判断

这轮工作最重要的不是多生成了多少页面，而是明确了一件事：

> demo 展示站的核心资产不是 Markdown 文件，而是 `public/` 里的原始示例和围绕它建立的生成链路。

一旦这个判断清楚，很多后续决定都会自然收敛：

- 页面应该自动生成，而不是手写维护。
- 导航应该来自 registry，而不是写死在配置里。
- 预览不是唯一真相，原始页面入口必须保留。

## 自测方式

本轮我用下面的方式做自测：

```bash
cd docs-site
npm ci
npm run generate
npm run build
```

重点关注：

- 生成脚本是否覆盖更多 demo。
- VitePress 是否能顺利读取生成的 sidebar。
- 构建产物里是否保留 `/public/**` 访问路径。

## 后续 backlog

这轮先把主链路打通，后面还有几个方向值得继续做：

1. 给 demo 增加人工元数据覆盖层，提升标题和描述质量。
2. 在首页加入“最近更新”或“推荐场景”维度。
3. 为无法在 Shadow DOM 中稳定运行的 demo 建立兼容名单和降级策略。
4. 把 docs-site 纳入统一的 workspace 脚本入口。
