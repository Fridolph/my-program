# VitePress 重构第二阶段详细设计

## 设计目标

第二阶段不再把站点当成手工维护的 Markdown 集合，而是把它当成“基于 `public/` 自动生成的展示系统”。

这套设计需要解决四个问题：

1. 如何从老 demo 目录中稳定发现内容。
2. 如何把内容映射为统一的站点页面。
3. 如何让导航自动追随内容变化。
4. 如何让隔离预览比第一版更稳定。

## 架构调整

### 1. 引入统一 registry

新增 `docs-site/scripts/demo-registry.mjs` 作为 demo 数据源层。

职责：

- 定义源目录到站点分类的映射。
- 扫描 `public/` 下全部 HTML 文件。
- 产出标准化 demo 元数据。
- 提供按分类分组和生成侧边栏的方法。

这样做的原因是，站点配置和页面生成不应该各自重复扫描文件系统。

### 2. 让生成脚本只负责“渲染”

`docs-site/scripts/generate-demo-pages.js` 现在不再自己判断分类和文件来源，而是直接消费 registry 结果。

职责：

- 重置并重新生成 `docs-site/demos/`。
- 输出首页、分类页、详情页。
- 输出 `.vitepress/generated/demo-sidebar.mjs`。

这样可以把“发现内容”和“输出页面”分离开，后续要改首页样式或详情页模板时，不需要改扫描逻辑。

### 3. 让 VitePress 配置消费生成产物

`docs-site/.vitepress/config.ts` 直接引入生成后的侧边栏模块。

收益：

- 站点导航与 demo 数据天然同步。
- 新增 demo 后不需要手写 sidebar。
- 分类数量和页面数量能自动反映到站点结构里。

### 4. 把生成接进开发与构建入口

在 `docs-site/package.json` 中增加：

- `predev`
- `prebuild`

这样无论本地开发还是生产构建，都会先执行生成脚本，避免 Markdown 页面滞后于 `public/` 内容。

## 预览组件修正

### 问题 1：重复 `attachShadow`

第一版刷新预览时会重复创建 Shadow Root，浏览器会直接报错。

处理：

- 如果 Shadow Root 已存在，就复用并清空内容。
- 如果不存在，再执行 `attachShadow`。

### 问题 2：相对资源路径失效

老 demo 里的 `src`、`href`、CSS `url(...)` 大多是相对路径，搬到站点详情页后会失效。

处理：

- 以 `demoUrl` 为基准重写资源地址。
- 同时处理 `head`、内联样式和容器内节点。

### 问题 3：脚本型 demo 只显示静态 DOM

直接用 `innerHTML` 注入内容时，脚本不会执行，导致 JS demo 失真。

处理：

- 重新创建脚本节点。
- 对外链脚本等待加载完成。
- 保留“在新窗口打开”作为兜底入口。

## 风险与边界

### 风险 1：并非所有旧 demo 都适合 Shadow DOM

某些 demo 可能强依赖全局 `document`、全局样式或历史浏览器行为，即使脚本重放后也未必完全还原。

策略：

- 默认优先提供可用预览。
- 无法完全兼容时，保留原始页面入口。
- 把“100% 兼容所有老 demo”放到后续 backlog，而不是卡住当前主链路。

### 风险 2：自动提取标题和描述精度有限

老 demo 的 HTML 结构不统一，标题和描述只能做启发式提取。

策略：

- 先保证字段完整可展示。
- 允许后续逐步补充人工元数据覆盖层。

## 验证方式

本轮以三类验证为主：

1. 运行生成脚本，确认 demo 数量与分类页数量明显提升。
2. 运行 VitePress 构建，确认配置和生成产物协同正常。
3. 抽样检查若干 JS / Canvas / 布局 demo，确认详情页可打开，预览至少可降级到外链模式。
