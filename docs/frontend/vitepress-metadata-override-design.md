# VitePress 人工元数据覆盖层详细设计

## 设计目标

自动扫描解决的是“内容能进站”，人工 metadata 覆盖层解决的是“内容进站后是否足够可读、可导航、可维护”。

这层设计要同时满足两个原则：

1. 不能破坏现有的自动发现主链路。
2. 必须让少量高价值 demo 能被人工精修。

## 为什么不用纯手工维护 Markdown

如果直接手写每个 demo 的标题和描述，短期看起来最精确，但长期会带来三个问题：

- `public/` 新增 demo 时容易漏同步。
- 页面数量增多后，维护成本会快速上升。
- 元数据与真实源文件脱节后，站点会再次回到“半自动、半手工”的混乱状态。

所以本轮不改“自动扫描 + 自动生成”的主架构，只增加一个轻量覆盖层。

## 数据结构

新增 `docs-site/scripts/demo-metadata-overrides.mjs`。

结构采用：

```js
export const demoMetadataOverrides = {
  'hover-transition/自制表情/index.html': {
    slug: 'emoji-face',
    title: '纯 CSS 表情符号',
    description: '...',
    tags: ['CSS3', 'Emoji', 'Hover'],
    difficulty: 'beginner'
  }
}
```

### 选择“相对 HTML 路径”作为 key 的原因

- 它和 `public/` 源文件是一一对应的。
- 即使标题变化，key 仍然稳定。
- 比用当前生成的 slug 更可靠，因为 slug 可能正是要被覆盖的对象。

## 合并策略

registry 先从 HTML 中提取默认 metadata，再按相对路径合并人工覆盖。

合并规则：

- `title`：如果有覆盖，直接使用覆盖值。
- `description`：如果有覆盖，直接使用覆盖值。
- `tags`：如果有覆盖，完全替换默认 tags。
- `difficulty`：如果有覆盖，使用覆盖值。
- `slug`：只参与 `id` 计算，不回写到源路径。

这样可以保证：

- 默认情况下仍能自动生成。
- 只有确实需要人工校准的项才被覆盖。

## 校验机制

为了避免覆盖层本身成为新的错误来源，需要在生成阶段增加两个校验：

### 1. 未知路径校验

如果 overrides 中配置的路径在 `public/` 下找不到对应 HTML 文件，直接报错。

这样可以避免：

- demo 删除后 override 残留。
- 手误写错路径却悄悄失效。

### 2. slug 冲突校验

覆盖后的 `id` 如果重复，直接报错。

这样可以避免：

- 两个 demo 被配置成同一路由。
- 生成出的详情页互相覆盖。

## 首批覆盖策略

本轮不追求一次把 74 个 demo 全部精修完，而是优先处理以下场景：

- 首页或分类页最容易被看到的 demo。
- 自动描述明显退化的 demo。
- slug 很难读的中文目录 demo。
- 标题过于原始、像文件名而不像站点内容的 demo。

## 后续扩展方向

如果这层机制跑稳，下一步可以继续向两个方向扩展：

1. 增加目录级 metadata 预设，减少同一系列 demo 的重复配置。
2. 给 overrides 增加截图、推荐级别、精选权重等展示字段。
